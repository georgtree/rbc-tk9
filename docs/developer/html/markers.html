Marker lifecycle and drawing¶

rbcGrMarker.c owns the marker registry, display list, shared commands and concrete marker classes. MarkerStruct contains common coordinates, axes, track association, visibility, tags and option state. Each concrete record adds its own resources and cached geometry. MarkerClass supplies configuration, mapping, drawing, export, point/region tests and cleanup. See Marker C reference for the shared graph-facing contracts.

Coordinates and mapping¶

Marker world coordinates are owned by the marker. Class mapping builds display geometry using its selected axes, anchor, pixel offsets and other type-specific options. Rbc_MapMarkers visits the display list and maps items selected by MAP_ALL or MAP_ITEM. Hidden markers and markers with no coordinates are skipped; a successful dispatch clears the item’s mapping flag.

The private marker HMap, VMap and MapPoint helpers are distinct from Rbc_HMap, Rbc_VMap and Rbc_Map2D. Marker parsing represents elastic Inf and -Inf endpoints using positive and negative DBL_MAX. These sentinels select normalized endpoints before applying descending direction and screen orientation. They must not simply be sent through the ordinary element-coordinate path.

The legacy marker logarithmic path also differs: positive values use log10, negative values are replaced with zero before normalization, and zero remains zero. It does not share the ordinary mapping helpers’ nonpositive-input rejection and overflow-safe normalization. This chapter describes existing behavior; consolidating those paths would require a separate compatibility change and tests.

Track-owned axes map against full world bounds, including the displaced part of a scrolled track. Visible bounds are for clipping. Each marker mapper also runs within a paired track viewport scope. Region tests can map original coordinates outside that drawing scope, so axis ownership must remain enough to select the proper full track extent. See Axes, mapping and track viewports.

Layers, order and visibility¶

The display list defines painter order. drawUnder selects the below-element or above-element pass. Drawing excludes hidden and wholly clipped markers, markers without coordinates, and markers associated with an existing hidden element. A missing associated element is not itself the same as a hidden one. The association check uses the element’s hidden state; do not assume it includes every element-specific visibility flag.

Ordinary graphs can batch compatible adjacent marker primitives. The component chooses eligibility and order; renderer services own native drawing targets and backend details. A new batch must flush at incompatible styles or intervening content so it preserves the original painter order.

Trackgraphs retain that order even when track-owned and graph-wide markers are interleaved. Track drawing uses renderer clipping for the visible owning rectangle, then enters the track viewport around class drawing. This clips complete native primitives without changing shared Tk graphics contexts. Graph-wide markers retain their graph-wide path. Window markers are handled separately rather than drawn into the clipping surface.

Window markers¶

A window marker manages a real Tk child. Mapping computes its size from the child’s requested dimensions and any positive explicit width/height, applies the anchor and pixel offsets, and tests its rectangle for overlap with the current plot viewport. Drawing moves/resizes and maps the child; the drawable argument is not used to paint that widget into a pixmap.

SyncWindowMarkers runs independently of the selected drawing layer. It processes both under/over windows, unmapping hidden or wholly clipped children and children in collapsed track regions. This is necessary because skipping a paint operation cannot erase an already mapped child, and the below-element backing store may be reused without repainting its markers.

Partial overlap deliberately retains existing graph behavior: the full child remains mapped and is clipped by its graph parent, not by the plotting area or track. There is no per-track clipping container. Do not describe this as the same clipping guarantee as a line, image or polygon marker.

Window-marker cleanup destroys its currently embedded child through ReleaseWindowMarkerChild. This ownership differs from borrowing an image or numeric source. Code that changes geometry management or child association must preserve event-handler and geometry-manager cleanup as well as pointer state.

XOR paths¶

Line and polygon markers retain native XOR behavior. Their configuration paths track whether old immediate geometry is present so it can be erased before replacement. Eligible graph-wide markers can use immediate drawing; track-owned markers use scheduled redraw and the track drawing path instead. Polygon immediate drawing has additional outline-only and axis-reset conditions.

XOR primitives bypass ordinary Cairo drawing where required. Old XOR geometry must be erased using its old geometry and compatible native state, not newly configured coordinates or an ordinary paint operation. Do not put XOR markers into the normal compatible-stroke batches or assume that redrawing them twice is harmless across changes of target or clipping. Document export is a separate class callback, not a capture of the screen’s XOR state.

Export and cleanup¶

Rbc_MarkersExport walks the same display list and selects the requested layer. It checks for an export callback, coordinates and visibility. Non-window track markers get an export clip around their class exporter and are skipped when wholly clipped or in collapsed regions. Window export follows its own path: it asks the renderer to export the child only when it is currently mapped. Backend capture support and export options determine the resulting content; the shared marker pass does not create an independently laid-out copy of the child widget.

Resource release is separate from record destruction. While the Tk window is live, Rbc_ReleaseMarkerTkResources invokes each initialized class’s cleanup, frees common coordinates and tags, releases axis references, and frees the Tk option record and table. Its release guard prevents repeating this work. DestroyMarker also handles failed initialization, removes bindings and registry/display-list membership, and frees the record. The whole-registry Rbc_DestroyMarkers then destroys marker tables and the display list. See Component configuration and resources and Graph lifecycle and redisplay for the broader ordering.

Changes should be checked with both marker layers, overlapping display order, track scrolling and inversion, child hide/remap transitions, XOR replacement, and resized document export. Screen snapshots alone do not establish child window ownership or correct binding and region-test behavior.

Common configuration and ownership¶

Concrete marker records embed Marker as their first member, checked by static assertions. Class methods receive that common header and recover the concrete record. MarkerClass combines Tk option specifications with configure, map, draw, export, point-test, region-test and cleanup callbacks. The common constructor chooses a class; it does not initialize Tk options or publish a registry entry. Arc construction reuses polygon storage and several polygon services, rather than introducing a second common marker lifecycle.

InitMarkerOptions temporarily detaches the preliminary name while applying component defaults through the option proxy. It uses the normalized marker name as resource name and the class UID as resource class. Monochrome alternatives are selected when available on a one-bit display. Both success and failure restore the preliminary name; an option-database name must not silently rename the new record or be freed twice during failed initialization.

ConfigureMarkerOptions installs candidate Tk fields under saved options, validates the name and calls the class configure method with optionMask. Reconfiguration cannot rename over another existing marker. The registry rename is committed only after class configuration succeeds. On failure Tk fields are restored and the diagnostic retained. This wrapper cannot undo derived resources that a class commits prematurely; each class must stage its own fallible work.

Common class preparation uses ParsedMarkerOptions. ParseMarkerOptions zeros it, parses tags, coordinates and state, acquires both axes and validates the optional track. The selected Y axis must belong to exactly that track, including the graph-wide NULL case. Failure releases candidate allocations and axis references. CommitMarkerOptions frees old common resources, transfers new allocations/references and clears transferred pointers. It does not register, map or schedule the marker; concrete configuration completes those tasks.

Coordinate and color parsing¶

Empty coordinates are accepted for every marker class and suppress normal mapping/drawing until populated. Nonempty coordinate lists obey these limits:

Coordinate-list arity¶

Class

Number of X/Y pairs

Text, window

Exactly one

Image, bitmap

One or two

Line

At least two

Polygon

At least three

Arc

Exactly two

Odd list lengths fail before allocation. Byte-size checks and Tcl_AttemptAlloc make coordinate allocation failure reportable as a Tcl error. Each component is evaluated separately. Exact Inf, +Inf and -Inf spellings select elastic DBL_MAX sentinels; other strings go through Tcl_ExprDouble. This parser does not impose a general finite-value policy.

Expression evaluation can execute application Tcl. The parser borrows list storage and the marker record throughout evaluation; ordinary candidate cleanup is not protection against callbacks deleting owners or mutating borrowed inputs. Future lifetime changes must address that boundary explicitly.

Single colors accept empty values as NULL and, when enabled by the caller, nonempty prefixes of defcolor as a sentinel. Other values acquire Tk colors. A color pair contains at most foreground and background. Pair conversion stages both colors, releases a successfully acquired first color if the second fails, and transfers ownership only on success. It does not free an older destination pair. Sentinel-aware release remains essential.

Creation, replacement and rename¶

CreateOp resolves the marker type and scans complete option/value pairs for the last abbreviated or full -name occurrence. Without one it generates a markerN name. The malformed trailing-option case is left to Tk configuration rather than reading past the argument vector. The concrete constructor copies the preliminary name; configured names must be nonempty and must not start with a dash.

Creation configures the new record before replacing an existing same-named marker. Replacement detaches the old record’s hash handle so its destructor cannot delete the entry being reused, then publishes the new value and appends its display link. This is destruction/recreation, not an in-place type change: class-owned resources of the old marker are released, including a managed child for a window marker. Reconfiguration uses different collision rules and rejects an existing destination name.

ConfigureOp validates the list of names before starting updates, but each marker update is its own transaction. A failure on a later marker leaves earlier successful updates in place. Query forms return information for the first named marker. Names are re-resolved as updates proceed, which matters if an earlier update renamed a marker.

DeleteOp ignores missing exact names, clears lookup diagnostics and schedules a redraw. ExistsOp tests the registry; NamesOp enumerates display order. Those views should agree in a valid registry/list state, but they are different structures and must be maintained together.

Bindings, point picking and region searches¶

Marker tags are interned in their own graph table. Binding enumeration appends name, class and configured tags in order. Tag strings can outlive a marker and can be registered before it exists. Deleting an object clears its object-pointer binding/current-item state; that is distinct from deleting scripts on an interned name tag.

marker get current checks the graph binding context before interpreting the current item as a marker. The handler does not accept coordinate picking or ordinary marker names; older legend-related comments here were misleading. Rbc_NearestMarker is the point-picking service: it traverses display order backwards and returns the first class point test that succeeds, not a global minimum-distance result.

The shared selection filters differ:

Shared query filters¶

Operation

Order and eligibility

Nearest point

Reverse display order; requested layer, coordinates present, not hidden, STATE_NORMAL

Region find

Forward display order; not hidden and no existing hidden associated element

Track-use query

Registry order; association only, regardless of visibility or coordinates

Both point and region queries enforce visible track constraints for local markers. Region overlapping mode intersects its query with track bounds; enclosed mode retains the original query rectangle after an intersection test. FindOp normalizes integer rectangle corners and returns only the first match. It does not filter by layer or marker state. Point picking does not repeat the associated-element hidden check used by region queries and drawing. These are current contracts, not interchangeable implementations of visibility.

The command dispatcher validates operation spelling and arity but does not itself refresh layout. Picking and class region methods consume current mapped state or use their own mapping helpers. Callers must not assume a command query implicitly performs the graph’s complete layout pass.

Display-order changes¶

RelinkOp resolves the target and optional reference before unlinking the existing display-list link. Invalid names leave both the registry and display order unchanged. Moving a marker relative to itself succeeds without changing order. A successful move retains the same marker and link, invalidates the backing store according to the moved marker’s under-layer setting (not the reference marker’s setting), and schedules redraw. Omitting the reference retains the existing front/back placement conventions.

Teardown and invalidation details¶

DestroyMarker invalidates the backing store for under-layer markers and removes object bindings. Initialized records use the guarded Tk-resource release path; records that failed before initialization receive explicit common cleanup. It then deletes non-NULL registry/list handles and frees the concrete allocation. Callers, rather than this destructor, schedule the eventual redraw.

Whole-registry destruction clears each marker’s hash handle before invoking its destructor so iteration owns hash-table deletion. It finally destroys both the registry and tag table and the display chain. This is final teardown, not a repeatable empty-the-registry operation on an otherwise initialized graph.

Rbc_MarkersUseTrack examines all registered associations to prevent removing still-used tracks or Y axes, including hidden markers. Rbc_MarkerFontsChanged likewise visits hidden text markers, resets text style and layout, rebuilds the rotated bounding outline and sets MAP_ITEM. Hidden geometry must be ready to remap when the marker is shown again.
